# Flask/Flask-Cors/Werkzeug/python-dotenv/python-engineio/python-socketio
# versions below were bumped together to close 18 real CVEs found by
# `pip-audit -r requirements.txt` (PyPA's own tool, backed by the PyPI
# advisory database — not guessed or assumed), most notably: Flask-Cors
# 4.0.1's regex path-matching bugs (PYSEC-2026-1383/1384/1385) could let
# CORS headers apply to routes they shouldn't — directly relevant here,
# since this app deliberately keeps the session-cookie-authenticated
# employer/admin portals OUTSIDE CORS scope (see API_PREFIXES in app.py);
# python-socketio 5.11.2's PYSEC-2026-1854 is a real deserialization RCE
# in multi-server pickle-based message-queue mode (this app doesn't
# currently configure SocketIO(message_queue=...), so wasn't reachable
# today, but costs nothing to close before it might be); Werkzeug's
# several safe_join/Windows-device-name issues and a multipart
# resource-exhaustion bypass; gunicorn's Transfer-Encoding request-smuggling
# pair (see its own pinned comment below for why that one needed a real
# `docker run` to confirm before bumping, not just a version pin). Full
# suite (SQLite + Postgres) and a live cross-origin CORS check
# (tests/test_cors.py) both re-verified passing after this bump, not just
# `pip check`.
Flask==3.1.3
Flask-Cors==6.0.0
Flask-SQLAlchemy==3.1.1

# Postgres driver — DATABASE_URL (see app.py / .env.example) already reads
# a postgres:// URL if set, but nothing could actually connect to one
# without this: SQLite (the zero-config default) has a hard single-writer
# ceiling that Phase 3 #19/#20 of the engineering review flags as a Severe/
# Critical gap for any real deployment scale. Installed unconditionally
# (not an extras group) so the DATABASE_URL override is guaranteed to work
# out of the box rather than failing at the moment an operator needs it.
psycopg2-binary==2.9.12

# Production WSGI server. Discovered via a real `docker run`, not guessed:
# once debug mode is correctly gated off in production (see the
# IS_PRODUCTION fix in app.py's `if __name__ == "__main__"` block),
# Flask-SocketIO's own run() refuses outright to use the Werkzeug dev
# server outside debug mode ("The Werkzeug web server is not designed to
# run in production"). eventlet gives Socket.IO's long-polling/websocket
# transports the concurrency model they need; gunicorn is only invoked in
# the Docker image (see Dockerfile) — local `python app.py` development is
# unaffected.
# S3-compatible client for off-site backup upload (scripts/backup.py) —
# works against self-hosted MinIO (docker-compose.backup.yml) or a real
# cloud bucket identically, since both speak the S3 API.
boto3==1.43.64

# Still pinned below the current latest (26.x) on purpose: 26.x's
# worker-class resolution switched to entry_points-based plugin discovery,
# which failed to find eventlet's worker class in this environment at
# build time ("Entry point ('gunicorn.workers', 'eventlet') not found") —
# a real incompatibility found via `docker run`, not assumed. Bumped from
# 21.2.0 to 22.0.0 to close a real Transfer-Encoding request-smuggling
# pair (PYSEC-2026-1433/1434, found via `pip-audit`) — re-verified via
# another real `docker build` + `docker run` + a live /healthz request
# (not just a version pin) that 22.0.0 still resolves the `eventlet`
# worker-class shorthand directly, the same as 21.2.0, and does NOT hit
# the entry_points issue that blocks 26.x.
eventlet==0.41.1
gunicorn==22.0.0
